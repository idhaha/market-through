# Quickstart: 증시캘린더 다중 소스 검증

## 준비

- Node.js >=20 환경에서 npm ci 후 서버를 재시작하고 서비스에 로그인한다.
- 기존 Puppeteer Chromium 또는 CENTRAL_BANKS_CHROMIUM_PATH의 실행 파일을 확인한다. 둘 다 없으면 Playwright Chromium 설치가 필요하다.
- 브라우저 개발자도구 Network에서 central-banks/image 요청을 확인한다.

## 수동 시나리오

1. 증시캘린더 최초 진입에서 기본 지표/실적 일정(Toss)이 표시되는지 확인한다.
2. 배당 일정에서 SEIBro iframe을 확인하고 원본 링크도 확인한다.
3. 각국 금리 일정을 선택한다. 화면 중앙의 '화면 로딩 중...' 이후 중앙 은행 / 현재 금리 / 다음 회의 / 마지막 변경 네 열과 주요 은행 네 개 이상이 있는 테이블 이미지만 표시되어야 한다. Investing iframe은 숨겨지고 원본 링크는 https://kr.investing.com/central-banks/ 이어야 한다.
4. 화면에서 이미지가 최대 800px 너비, 높이 자동, 상단 여백 30px로 표시되는지 확인한다. 작은 화면에서도 영역 너비를 넘지 않아야 한다.
5. 다른 메뉴와 소탭으로 이동 후 돌아온다. 같은 날에는 화면 캐시로 이미지를 보여주고 추가 이미지 API 요청이 없어야 한다. 새로고침 버튼을 누르면 force_refresh=true API 요청과 외부 재캡처가 발생하고 새 이미지로 교체되어야 한다. 완료 후 재진입은 갱신된 이미지를 재사용한다. 반복 클릭은 진행 중 요청을 공유해야 한다.
6. 페이지를 다시 연다. 화면 캐시는 초기화되어 이미지 API 요청이 발생할 수 있지만 서버의 당일 캐시로 추가 외부 캡처 없이 응답해야 한다. 마지막 공급자 선택 유지도 확인한다.
7. 최초 조회 도중 소탭을 반복 클릭한다. 화면 요청을 공유하며 현재 소탭의 상태가 이전 요청으로 덮어쓰이지 않아야 한다.
8. 한국시간 날짜 변경 후 다음 진입/조회에서 새 캡처가 발생하는지 확인한다. 모의 검증으로 날짜를 변경할 수 있다. 자정에 자동 실행되는 동작은 요구하지 않는다.
9. 외부 접근 실패 또는 이미지 API 오류를 유도한다. 로딩 메시지가 오류/새로고침 안내로 바뀌고 다음 새로고침에서 재시도해야 한다. 다른 공급자는 사용 가능해야 한다.
10. 네트워크 지연을 적용한다. 중앙 로딩 메시지는 응답뿐 아니라 이미지 디코딩 완료까지 유지되고 aria-busy가 true에서 false로 바뀌어야 한다.
11. Toss/SEIBro 새로고침은 기존 iframe 재로드를 유지하는지 확인한다.
12. 서버 재시작 후 첫 이미지 요청은 새 캡처를 수행하는지 확인하고 PNG/debug 이미지 파일이 생성되지 않는지 확인한다. 성공·실패 후 캡처 브라우저도 종료되어야 한다.

## 수행된 검증 — 2026-10-05

- 실제 Investing.com 중앙은행 테이블 PNG: 49,141바이트, PNG 시그니처 확인. 이 실캡처는 기본 대기 3초 단계에서 수행했으며 이후 1초 변경은 구문 검사 완료; 1초 설정의 실제 사이트 재검증은 대기.
- 테이블 헤더·은행 수 판별, 한국시간 날짜 경계, 당일 캐시, 동시 요청 공유, 실패 후 재시도: 모의 검증 통과.
- headless 브라우저에서 화면 캐시·이미지 렌더·숨겨진 iframe 및 지연 응답 중앙 메시지/디코딩 완료 후 교체: 통과.
- public/app.js, central-banks.js, server.js 구문 검사: 통과.
- 전체 앱의 공급자 저장 복원, 운영 배포·자원 사용 및 위 수동 시나리오 전체 완료는 아직 확인하지 않았다.

## 추가 새로고침 검증 — 2026-10-06

- 성공 이미지가 있는 상태에서 새로고침 요청을 실패시킨다. 오류 안내 후 다른 메뉴로 갔다가 돌아오면 기존 성공 이미지를 다시 표시해야 한다. 새로고침 버튼을 다시 누르면 재조회해야 한다.
- 성공 재캡처 뒤 조회 시각이 갱신되고 다음 일반 진입에서는 추가 API 요청 없이 갱신된 이미지를 재사용하는지 확인한다.
